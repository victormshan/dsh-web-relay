# Skill: auto-iteration-modeling

> 用途：仅在 **自动版本迭代** 场景下使用。
> 归属：工作模式 / 方法论 Skill。
> 适用范围：dsh-web-relay 或类似的源码级自动多版本迭代任务。
> 不适用范围：普通问答、普通代码修改、手动单版本开发、非迭代式重构。

## 1. 何时激活

当任务满足以下条件时，本 Skill 才应被加载：

- 用户明确要求“自动迭代 N 个版本”
- 或当前处于 AutoIteration 模式（如 v1.9 AutoIteration）
- 或任务要求“在上一版本基础上连续增加多个版本”

### 何时不激活

- 用户只是要求修一个 bug / 加一个小功能
- 用户只要求单次版本升级，不涉及多版叠加
- 当前是普通问答或文档整理
- 当前处于手动逐步开发流程（每一步由用户确认）

如果本 Skill 与其他工作模式冲突，优先以用户当前明确指定的模式为准。

## 2. 核心原则

每次版本迭代前，必须完成现状建模，再进入设计/实现。

禁止：

- 不画图直接改代码
- 改 A 功能时不分析是否影响 B 功能
- 在没有功能树/调用链的情况下盲目重构

## 3. 每次迭代前必做的最小建模集合

### 3.1 功能树状图

按功能分层列出当前能力。示例结构：

```text
项目
├── 协议层
├── Provider 层
├── 状态管理层
├── UI 层
└── 基础设施
```

### 3.2 当前代码调用流程图

画出一条真实请求的路径。示例：

```text
用户输入
  → 入口 handler
  → Provider 调用
  → 结果保存
  → 解析/执行
  → 唤醒/收口
```

### 3.3 版本演进图

画出：

```text
当前版本（现状）
下一版本 = 当前 + 新增功能
再下一版本 = 下一版本 + 新增功能
```

### 3.4 影响面标注

每次改动前必须列出：

```text
本次改动模块
会影响的模块
可能受影响的测试
```

## 4. 复杂版本额外补充

- 状态机图（如果涉及状态流转）
- API/协议契约图（如果涉及接口变更）
- 数据模型图（如果涉及数据结构）
- 测试矩阵

## 5. Step 0 模板

每个迭代版本开始前，先输出 Step 0：

```text
Step 0：现状建模
├─ 0.1 功能树状图
├─ 0.2 当前代码调用流程图
├─ 0.3 模块依赖/影响图
├─ 0.4 状态机图（如涉及）
├─ 0.5 API/接口清单
├─ 0.6 本次改动点标注
└─ 0.7 需要重构/隔离的模块
```

只有 Step 0 完成后，才进入：

```text
Step 1：设计本版新增功能
Step 2：实现
Step 3：测试
Step 4：提交/打 tag
```

## 6. 模块化重构建议

如果发现某个模块存在以下情况，应在本轮迭代前提出重构建议：

- 一个函数承担多种职责
- 多个相似 Provider/分支使用 if/else 堆叠
- 修改一个功能需要改动多处无关代码

建议使用策略/接口模式隔离变化，例如 Provider 层抽象。

## 7. 与其他工作模式的关系

本 Skill 是**自动迭代专用流程**，不替代：

- 普通手动开发模式
- 标准编码 Agent 工作流
- 其他项目专属规范

使用前先判断：

```text
当前是否处于自动版本迭代？
如果是 → 加载本 Skill
如果不是 → 不要套用本 Skill 的 Step 0 强制建模流程
```
